## 1. Goal

Build a new standalone Android dashcam app that:

1. Continuously records video in a rolling buffer while driving (fork of Alibi's recording engine — batches auto-expire, "Save" concatenates the retained window into one file).
2. Burns a **permanent watermark into the saved video** showing:
   - Date as `YYYY-MM-DD`
   - Time as `HH:MM:SS`
   - Current speed (from GPS)
   - Updated live, frame-to-frame, as the car moves — not a static stamp.
3. Automatically detects hard-braking/impact events via the accelerometer and extends/finalizes a save so the incident is captured with context before *and* after it (§7).
4. Has a UI reworked around **FadCam's design language** (dark-first theming, traffic-light recording controls, card-rail dashboard, bottom-sheet pickers, live-preview settings) — but implemented in **Jetpack Compose** (Alibi's stack), not FadCam's XML/Java stack. We are porting *design principles*, not code.
5. Works correctly in **split-screen / multi-window** mode (e.g., left half = this app, right half = a navigation app), with recording continuing uninterrupted regardless of window focus/size.
6. **Has zero dependency on Google Play Services** anywhere in the stack (confirmed hard requirement — see §16). Every subsystem below (location, fonts, etc.) is designed around this constraint explicitly, not just "where convenient."

## 4. Functional Requirements Summary

1. App launches directly into a live camera preview with a large, obvious record control (dashcams are typically mounted and expected to auto-record on launch — see §9.1 for an "auto-start on launch" setting).
2. Recording runs as a rolling buffer: configurable retention window (reuse Alibi's 1 min–10 days range; sensible dashcam default: 30–60 min, since loop-recording dashcams typically use shorter windows than Alibi's privacy use case).
3. Two save paths, both reusing the same underlying concatenation mechanism (§5.4):
   - **Manual save**: user taps "Save current buffer" — protects/finalizes the currently-retained window immediately, unchanged from Alibi's existing behavior.
   - **Automatic impact save**: a hard-braking/collision-like deceleration event is detected via the accelerometer, which protects the current buffer immediately but **delays finalizing** the saved file until a configurable duration (**default 5 minutes**) of additional recording has elapsed, so the incident's aftermath is captured too. Full design in §7.
4. Every saved (and in-progress) video frame has a burned-in watermark: `YYYY-MM-DD HH:MM:SS` plus current speed (unit configurable: km/h or mph), top-left or user-configurable corner, semi-transparent backing plate behind text for legibility over bright/dark road footage.
5. Watermark is controlled by a single settings toggle: **"Show watermark"** (on/off). When on, it is both shown in the live preview and burned into the saved file — the live preview must be a truthful WYSIWYG representation of what gets saved (this is how FadCam's `renderToPreview()`/`renderToEncoderInternal()` pairing works, and we replicate that guarantee).
6. If GPS has no fix, speed line degrades gracefully to a "Speed: --" placeholder (mirrors FadCam's "GPS is off" fallback text) rather than blocking recording or crashing.
7. User can browse, play, rename/export (share sheet), and delete saved recordings from a Recordings screen; auto-saved (impact-triggered) clips are visually distinguished from manually-saved ones (§7.3).
8. App is fully usable in Android split-screen/freeform multi-window mode alongside another app (e.g. Google Maps) at roughly half-screen width, and recording is never interrupted by losing window focus or being resized.
9. App requests only the permissions it needs: camera, microphone (if audio track is enabled), location (for speed), notifications (foreground service), and storage as required by target SDK. **No network permission and no Google Play Services dependency anywhere** — this app is fully offline and Play-Services-free by hard requirement (§16), matching and extending Alibi's already-offline design.
10. The Record screen has a Cut/Uncut control that hides/shows the live preview on demand, without pausing or otherwise affecting the recording itself — a driver can black out the screen (e.g. to avoid glare at night) while everything keeps recording normally underneath. Full design in §9.1.
11. When the app is backgrounded while actively recording, an optional floating "picture-in-picture" preview window (off by default, opt-in via Settings and a system "draw over other apps" grant) shows the live feed with a single Pause/Resume control, so the driver can glance at or pause recording without switching back to RoadLog. Full design in §9.5.

## 5. Watermark Subsystem (core technical design)

### 5.1 Compositing approach: CameraX Effects API, not a hand-rolled EGL pipeline

**Decision:** Alibi already builds its video capture on CameraX (`androidx.camera:camera-core/camera2/lifecycle/video/view` 1.3.4 — confirmed in `alibi/app/build.gradle`). CameraX ships an official **Effects API** (`androidx.camera:camera-effects` artifact) that lets you insert a custom `SurfaceProcessor` into the camera pipeline, attached to one or more use cases (`Preview`, `VideoCapture`) via `UseCaseGroup.Builder().addEffect(CameraEffect(...))`. This is the supported, maintained way to do exactly what we need: composite a GL layer on top of the camera frames before they reach the preview surface and the video encoder, simultaneously.

**Version actually used:** `androidx.camera:camera-effects:1.4.2`, and the whole CameraX stack (`camera-core`/`camera-camera2`/`camera-lifecycle`/`camera-video`/`camera-view`/`camera-extensions`) bumped from Alibi's 1.3.4 to match. The current-stable line at implementation time is actually 1.6.1 (newer than this plan's original 1.5.1 guess), but 1.5.x/1.6.x both require AGP 8.6+ (1.6.x additionally requires `compileSdk 36`) — this project is on AGP 8.3.0/compileSdk 35, the same AGP-floor tradeoff already hit and documented for `media3-transformer` (§13). 1.4.2 is the newest patch that resolves against the current toolchain; revisit alongside the AGP/compileSdk bump that media3-transformer is also waiting on.

This is **preferred over porting FadCam's `GLRecordingPipeline`** (manual EGL14 context + `Camera2` capture session + `MediaCodec.createInputSurface()` + `MediaMuxer`/fragmented-MP4 muxer) because:
- FadCam needs that manual pipeline for reasons we don't have (dual-camera picture-in-picture compositing, fragmented-MP4 zero-corruption muxing). Building and maintaining a hand-rolled EGL/Camera2/MediaCodec stack is a large, fragile undertaking (FadCam's `GLWatermarkRenderer.java` alone is ~2858 lines, with manual EGL surface-loss recovery, rotation matrices, etc.) — don't take on that maintenance burden for "burn in a text overlay."
- CameraX's Effects API gives us the encoder-surface + preview-surface dual-compositing guarantee "for free," which is the one property we actually need from FadCam's design (what you see is what gets saved).
- It keeps Alibi's existing `VideoRecorderService`, camera lifecycle, lens switching, quality presets, and torch handling untouched — we're adding one `CameraEffect`, not replacing the capture stack.

**What was actually built — `OverlayEffect`, not a hand-rolled `SurfaceProcessor`.** This plan originally called for implementing `WatermarkSurfaceProcessor implements androidx.camera.core.SurfaceProcessor` directly — manual EGL passthrough shader for the camera texture, a second textured-quad shader pass for the watermark, manual `SurfaceOutput` fan-out and transform-matrix rotation handling. Inspecting the actual `camera-effects` 1.4.2 AAR (`androidx/camera/effects/OverlayEffect.class`) found that CameraX already ships a purpose-built, official `CameraEffect` subclass for exactly this scenario: **`androidx.camera.effects.OverlayEffect`** composites a plain `android.graphics.Canvas` — the same `Canvas`/`Paint` API FadCam's rasterization technique uses — onto camera frames, handling all of the GL/EGL/texture-upload/multi-`SurfaceOutput`-fan-out plumbing internally. This is strictly less code and less risk than the raw-`SurfaceProcessor` approach originally planned, while providing the exact same guarantee (composited onto every output surface, WYSIWYG). Concretely:
1. `WatermarkOverlay` owns an `OverlayEffect(CameraEffect.VIDEO_CAPTURE, queueDepth, handler, errorListener)` on a dedicated background `HandlerThread`, and calls `.setOnDrawListener { frame -> ... }`.
2. Each draw callback (`WatermarkRenderer.draw`) clears `frame.overlayCanvas` (the surface persists across frames — must be explicitly cleared each time, `PorterDuff.Mode.CLEAR`), then draws the backing plate + text directly onto it — no separate bitmap-to-texture upload step is needed (unlike the original plan, since `OverlayEffect` already owns the texture), but the "size text proportionally to width, clamp ~16–48px" technique (FadCam's `0.020 × encoderWidth`) carries over unchanged.
3. `OverlayEffect` fans the composited result out to every `SurfaceOutput` internally — no separate "preview vs. encode" branching needed, same guarantee the original plan wanted from a hand-rolled processor.
4. **Rotation is not free, unlike this plan originally hoped.** CameraX's own Javadoc for `Frame.getRotationDegrees()` states: "The app must draw the overlay according to the rotation degrees to ensure it is displayed correctly to the end users" — the overlay canvas is in raw sensor-buffer coordinates, not final display orientation. `WatermarkRenderer` compensates by rotating/mirroring the canvas (`frame.rotationDegrees`, `frame.isMirroring`) before drawing in upright, "top-left as the viewer sees it" coordinates.

**Real-device bug found and fixed post-implementation.** The first version of this compensation used `canvas.rotate(+rotation)`. Confirmed on-device, this was backwards: `Frame.getRotationDegrees()`'s Javadoc describes a clockwise rotation that gets applied *to the frame* for it to display correctly, meaning content drawn in upright/logical space must be **pre**-rotated by the *opposite* (counter-clockwise) amount so that later rotation brings it back to upright — i.e. `canvas.rotate(-rotation)`. Using `+rotation` put the watermark 2× the intended rotation off from correct; for the common `rotation=90` case that's 180° off, which is exactly the reported symptom ("top-left watermark appears bottom-right, upside down"). Fixed by negating the angle. This was compounded by a second, related bug (see §9.1/§10.2's implementation notes below): `VideoRecorderService` never told CameraX about device rotation changes at all, so `frame.rotationDegrees` itself could be stale — both the raw camera image and the watermark's compensation depend on the same value, which is why both symptoms were reported together and both are fixed by the same underlying change.

**Scope boundary for this phase — encoder path only, not the live preview yet.** `VideoRecorderService` currently binds only `VideoCapture` (no `Preview` use case — the pre-recording "framing" preview in `VideoRecorderPreparationSheet`/`CameraPreview.kt` is a *separate*, independently-bound `Preview` use case tied to the Activity/Compose lifecycle, not the recording service). A `CameraEffect`'s `targets` must match use cases actually present in the same `UseCaseGroup` — `CameraEffect.VIDEO_CAPTURE` is used here, matching the group's only use case. This means **the saved file is watermarked, but no live preview shows it yet** — that requires binding `Preview` and `VideoCapture` together in one `UseCaseGroup` sharing the same effect, which is §9.1's "full-bleed live camera preview, watermark visibly composited on top" work (a later phase rebuilding the Record screen around FadCam's design), not this one. Wiring the live preview into the same effect chain is that phase's job, not a gap in this one.

### 5.2 `WatermarkTextProvider` — text assembly

Modeled directly on `FadCam/app/src/main/java/com/fadcam/watermark/WatermarkManager.java`, simplified to our scope (no reverse-geocoding, no UTM, no weather/noise/compass lines — just what's requested):

```kotlin
class WatermarkTextProvider(
    private val locationTracker: LocationTracker,   // §6
) {
    fun currentText(settings: WatermarkSettings): String {   // §11
        // "2026-07-16 14:32:07"
        val timestamp = FORMATTER.format(Instant.now().atZone(ZoneId.systemDefault()))
        // "58 km/h" or "-- km/h" if no fix, or "36 mph" per unit setting
        val speed = locationTracker.currentSpeedText(settings.speedUnit)
        return "$timestamp\n$speed"
    }
}
```

(Built taking `settings` as a per-call parameter rather than a `Flow` held in the constructor — the caller, `WatermarkOverlay`, already re-reads current settings once per frame via a plain supplier function, so there's no need for `WatermarkTextProvider` itself to collect a `Flow`.)

`WatermarkCorner`/`WatermarkSettings` (§11) were added to `AppSettings.kt` as part of this work, ahead of the rest of §11's schema additions (`LocationSettings`, `ImpactDetectionSettings`, `autoStartOnLaunch`) — `WatermarkTextProvider`/`WatermarkRenderer` need real corner/speed-unit/enabled values to be genuinely wired rather than stubbed, so `val watermark: WatermarkSettings = WatermarkSettings()` is already on `AppSettings`'s root today, not deferred to the settings-schema phase.
Called once per rendered frame from `WatermarkSurfaceProcessor` (§5.1 step 3) — cheap enough (string formatting + a cached last-known-speed read) to call at full frame rate that no throttling was originally thought necessary, unlike FadCam's geocoding-heavy version.

**Resource-consumption optimization, applied later, not a behavior change.** "Cheap enough to call at full frame rate" undersold the actual cost once measured against what this method does 30-60 times a second while recording — the only genuinely hot, continuously-running path in this whole app. `currentText()` now caches its result keyed on the current epoch-second (the displayed timestamp's own granularity) plus the current speed text, so `DateTimeFormatter.format()` and the rest of the string assembly only actually run when one of those inputs has changed — at most once a second in practice, not once a frame — while returning bit-for-bit the same string a caller would have gotten anyway at that instant. `WatermarkRenderer.draw()` got the equivalent fix on the drawing side: it used to call `text.split("\n")` and `Paint.measureText()` fresh on every frame regardless of whether `text` had actually changed since the last one; now both are cached and only recomputed when the text or the text size (itself width-dependent, so only changes on rotation/resolution changes) actually differs from the last frame's.

- Semi-transparent dark backing plate behind text (`Paint` with `setShadowLayer` alone, as FadCam does, is often not enough for bright sky/road backgrounds — add a translucent black rounded-rect behind the text block for reliable legibility; this is an improvement over FadCam's shadow-only approach, worth calling out to the implementer as a deliberate deviation).

### 5.4 Interaction with the rolling-buffer/batch architecture

Because the watermark is burned in continuously at capture time (not as a post-processing pass), each ~60s batch file already contains correctly-timestamped, per-frame watermark text when it's written. Concatenation (`BatchesFolder.concatenate`, implemented via `androidx.media3:media3-transformer`) simply joins already-watermarked segments at save time — for either a manual save or the impact-triggered delayed save described in §7 (which just concatenates a larger/differently-bounded set of the same kind of batches).

**Why FFmpeg isn't used for this:** Alibi originally used `com.arthenica:ffmpeg-kit-full-gpl` for stream-copy (`-c copy`) concatenation. That artifact was pulled from Maven Central in April 2025 when the upstream FFmpegKit project retired, and the obvious replacement — a community fork under `com.antonkarpenko`'s namespace — was evaluated and rejected: brand-new individual-maintainer namespace, no reputation signal, shipping prebuilt native binaries inside an app with camera/mic/location permissions is an unacceptable supply-chain risk.

**Replacement: Media3 Transformer, relying on automatic transmuxing.** Build a single `Composition`/`EditedMediaItemSequence` containing one `EditedMediaItem` per input batch file (in order) and run it through a `Transformer` with default settings. Transformer inspects each input's track format and **transmuxes** (copies compressed samples byte-for-byte, no decode/encode cycle) whenever an input's format already matches the requested output format — which is guaranteed here, since every batch comes from the same CameraX/MediaCodec encoder configuration recorded back-to-back on one device. This is the exact same "no re-encode" guarantee `-c copy` gave us, just decided automatically by Transformer instead of via an explicit codec flag; there is no equivalent to FFmpeg's old "try `-c copy`, fall back to `-c:v copy -c:a aac`, ultimately fall back to full re-encode" cascade, because the transmux-eligibility precondition (matching formats) always holds for this app's batches.

**One real constraint this introduces:** `Transformer.start()` can only write to a local absolute file path — it cannot write directly to a SAF tree `Uri` or a scoped-storage `MediaStore` `Uri` (confirmed still-open upstream: https://github.com/androidx/media/issues/504). This matters because `BatchesFolder`/`VideoBatchesFolder` support saving to three destination kinds (`BatchType.INTERNAL`, `CUSTOM` via SAF, `MEDIA` via MediaStore on API 29+). The fix is a standard, well-understood pattern: when the destination is a SAF/MediaStore `Uri`, Transformer exports to a temp file in `context.cacheDir` first, then the temp file's bytes are stream-copied into the destination `Uri` via `context.contentResolver.openOutputStream(uri)`, then the temp file is deleted. `BatchType.INTERNAL` (and `MEDIA` on API<29, which is also a plain filesystem path) need no such workaround — Transformer writes directly to the final path.

**Consolidation note:** this is the same `androidx.media3` dependency family already planned for the Recordings/Gallery screen's in-app player (`media3-exoplayer` + `media3-ui`, §9.2/§13) — a later phase, not part of this concatenation work — so adopting Transformer here doesn't introduce a new third-party dependency tree, it front-loads part of one that was already on the roadmap.

Verify during implementation that concatenation is actually transmuxing (not re-encoding) for real recorded batches — e.g. by checking export duration is near-instant relative to input duration, or by inspecting `Transformer.Listener.onCompleted`'s `ExportResult` — since re-encoding would be unnecessary and slower once frames are already watermarked, and would silently defeat the point of relying on transmux eligibility.

### 5.5 "Silent Watermark": full pipeline teardown when disabled (energy-efficiency pass)

**Real, always-on-regardless-of-setting cost found and fixed.** Turning `settings.watermark.enabled` off previously only skipped drawing text inside `WatermarkRenderer.draw()` (`watermark/WatermarkRenderer.kt`) — the `OverlayEffect`/`CameraEffect`, its dedicated `HandlerThread` (§9.1's `THREAD_PRIORITY_URGENT_DISPLAY` fix), and the whole GPU compositing pass stayed fully constructed and attached to the `UseCaseGroup` for the entire session regardless, with `draw()` just clearing the canvas and returning every frame. Fixed in `VideoRecorderService.openCamera()`: `watermarkOverlay`/`secondaryWatermarkOverlay` are now only constructed, and `.addEffect(...)` only called on the `UseCaseGroup` builder, when `settings.watermark.enabled` is true — watermarking off now means the GPU compositing pass and its dedicated thread never exist at all, not just that they render nothing.

**A related, cross-subsystem fix in the same pass:** `LocationTracker`'s *only* consumer anywhere in the app (confirmed by grep) is `WatermarkTextProvider`'s speed readout — nothing else ever reads a GPS fix. `IntervalRecorderService.start()` now skips `locationTracker.start(...)` entirely when watermarking is disabled, so the GPS radio isn't kept warm at `settings.location.updateIntervalMs` for a value nothing reads. Same `lateinit settings` snapshot limitation as every other video/watermark setting applies — toggling mid-recording needs a restart to take effect, already true today for this whole settings group.

## 6. Location / Speed Subsystem

**New component:** `LocationTracker`, built on **`android.location.LocationManager`** (`LocationManager.GPS_PROVIDER`) directly. **Not** `FusedLocationProviderClient` / Google Play Services location — this app has a hard requirement to avoid Google Play Services entirely (§16), so this is not a "prefer if available" choice, it's the only implementation.

- `requestLocationUpdates(GPS_PROVIDER, minTimeMs = 1000L, minDistanceM = 0f, listener)` — ~1Hz updates, matching typical dashcam speed-refresh expectations.
- Prefer `Location.getSpeed()` (device-reported instantaneous speed, itself GPS-Doppler-derived on most chipsets — accurate and low-jitter) over manually differentiating consecutive lat/lon fixes; only fall back to manual delta-distance/delta-time calculation if `hasSpeed()` is false or accuracy is poor (mirrors why FadCam's `SensorDataProvider.getSpeedKmh()` exists as a dedicated abstraction — keep that same separation of concerns).
- Convert m/s → km/h (`× 3.6`) or mph (`× 2.23694`) per the user's unit setting.
- Expose `currentSpeedText(unit): String` returning `"-- km/h"` when no fix / stale fix (>5s old) is available, so `WatermarkTextProvider` never blocks on missing data.
- Without Play Services' fused location, cold-start GPS fix acquisition can be noticeably slower (especially indoors/parking garages) — the "-- km/h" fallback text already covers this gracefully; no special handling needed beyond that, but worth calling out as an expected UX characteristic, not a bug, when testing (§15).
- Lifecycle: start location updates when the rolling-buffer recording service starts; stop when it stops. Location updates must keep flowing even when the app is backgrounded/split-screen (see §10) since recording is service-driven, not activity-driven — this already works correctly by virtue of reusing Alibi's service-based recording architecture.

### 6.1 Permissions

- `ACCESS_FINE_LOCATION` (required, request at runtime with rationale on first launch — extend Alibi's `WelcomeScreen` onboarding flow to include this request alongside camera/mic).
- `FOREGROUND_SERVICE_LOCATION` (Android 14 / API 34 foreground service type — add alongside Alibi's existing `FOREGROUND_SERVICE_CAMERA`/`FOREGROUND_SERVICE_MICROPHONE` types on the recording service's manifest entry).
- `ACCESS_BACKGROUND_LOCATION` is **not** required — an active foreground service already grants location access without needing the separate background-location permission/dialog, since the app is always visible-via-notification while recording. Do not request it; it triggers Play Store's stricter background-location review process for no benefit here.

**Implementation notes.** `LocationTracker` itself only ever passively checks this permission and degrades gracefully if it's missing (§6) — it never actively prompts. Before this final pass, nothing in the app ever called `requestPermissions` for `ACCESS_FINE_LOCATION` at all, meaning a real user would never see a system permission dialog for it and the watermark's speed line would always read "-- km/h" by default. A new dedicated onboarding page (`LocationPermissionPage`, inserted into `WelcomeScreen`'s pager) closes this gap, using the same `PermissionRequester` component already used elsewhere in the app for camera/mic/storage requests — with an always-visible "Skip" action, since this permission is optional and must never be a dead end (declining it, or permanently denying it, still lets onboarding continue). `VideoRecorderService.startForegroundService()` now conditionally includes `ServiceInfo.FOREGROUND_SERVICE_TYPE_LOCATION` in its `startForeground()` call — conditionally, checking `ACCESS_FINE_LOCATION` is actually granted at that moment, mirroring how the microphone type is already conditional on `enableAudio` — since Android 14+ throws if a foreground service declares a type whose runtime permission isn't held, and location here must never be able to block a recording from starting.

## 7. Impact Detection & Auto-Save on Hard Braking

A wholly new feature (neither source repo has anything like it): detect a hard-braking or collision-like deceleration event via the accelerometer, and automatically protect + extend the saved clip so it captures context both before and after the event, without requiring the driver to react and tap Save manually.

### 7.1 Detection approach

- Use `SensorManager` with `Sensor.TYPE_LINEAR_ACCELERATION` (gravity-compensated — more reliable for isolating a deceleration spike than raw `TYPE_ACCELEROMETER`, which also carries the gravity vector), registered at `SensorManager.SENSOR_DELAY_GAME` (~20ms/50Hz). This sampling rate needs no special runtime permission — Android's `HIGH_SAMPLING_RATE_SENSORS` permission is only required above 200Hz, which is unnecessary here.
- Compute the magnitude of the 3-axis acceleration vector on each sample; trigger when magnitude exceeds a threshold (tune during implementation — a starting point around 2.5–3g sustained for a couple of consecutive samples, not a single-sample spike, to reduce false positives from potholes/speed bumps) using a small rolling-window/debounce check rather than a raw instantaneous threshold.
- **Known limitation to document for users, not "fix" in code:** detection quality depends on the phone being securely mounted to the vehicle (a loose phone in a cupholder will generate spurious spikes from handling, not the car's motion) — this is a standard caveat for all consumer dashcam G-sensor features, not unique to this design.
- The existing manual "Save current buffer" button (from Alibi, unchanged) remains available at all times as a direct, immediate save — the delayed-extension behavior below is specific to the *automatic* impact trigger, not the manual button, per the original request scope. (Note for a possible future enhancement, not required now: the same delayed-extension behavior could optionally be offered on the manual button too.)

### 7.2 Auto-save timing behavior

At detection time `T`:
1. **Immediately** protect all currently-retained batches from the rolling buffer's normal expiry/deletion — same mechanism the manual "Save" flow already uses (Alibi's `BatchesFolder`) — this preserves the "before" footage (whatever's currently in the buffer, per the user's configured retention window).
2. **Do not finalize/concatenate yet.** Schedule a pending "extend and finalize" action for `T + postImpactDurationMinutes`.
3. Recording continues completely normally in the interim — new batches keep being produced by the rolling buffer as usual.
4. At `T + postImpactDurationMinutes`, finalize: concatenate [protected pre-impact batches] + [all batches recorded between `T` and `T + duration`] into a single output saved file, using the exact same Media3 Transformer transmuxing-based concatenation as manual save (§5.4) — just a larger, differently-bounded input set.
5. Show a persistent, dismissible in-app banner + notification while a save is pending/counting down (e.g., "Incident detected — finalizing clip in 4:32") with a **Cancel** action, so the driver can abort an obvious false positive (e.g., a pothole) rather than needlessly consuming storage.

### 7.3 Settings & UI touchpoints

```kotlin
@Serializable
data class ImpactDetectionSettings(
    val enabled: Boolean = true,
    val postImpactDurationMinutes: Int = 5,   // default per requirement; user-configurable
)
```

- **Settings screen:** new "Impact Detection" card — enable/disable toggle, and a "minutes to keep recording after impact" picker (bottom-sheet number picker, same pattern as other value pickers, §9.3).
- **Record screen:** small banner/indicator while a pending auto-save countdown is active, with the Cancel action from §7.2 step 5.
- **Recordings/Gallery screen:** auto-saved (impact-triggered) clips get a small distinguishing badge (e.g., "Auto-saved") versus manually-saved clips, so the driver can immediately spot incident clips in the list (§9.2).

### 7.4 Reliability: surviving process death mid-countdown

The pending-save wait (up to several minutes) must not be lost if the app process is killed and restarted before it completes.

- **Primary mechanism:** run the wait as a coroutine `delay()` inside the recording foreground `Service` itself — since the whole app's design already depends on this service staying alive continuously while recording (it's a foreground service with a persistent notification, which Android is strongly reluctant to kill), this is reliable in the overwhelming majority of cases and requires no extra permissions (avoids `AlarmManager`'s exact-alarm permission complexity on Android 12+, which isn't warranted for a "keep recording ~5 more minutes" tolerance where a few seconds/minutes of drift is harmless).
- **Safety net:** persist the pending trigger's timestamp and the protected-batch reference (e.g., a small JSON record alongside the existing DataStore-backed settings, or a dedicated pending-action file next to the batches folder) whenever a trigger fires. On every service start, check for a persisted pending record: if `now >= T + duration`, finalize immediately; if not, resume waiting for the remainder. This covers the rare case of a low-memory system kill between trigger and finalize.
- Explicitly test this path (force-stop the app mid-countdown, relaunch, confirm correct finalize behavior) — see §15.

### 7.5 Implementation notes

`ImpactDetector` (§7.1), `PendingImpactSave`/`PendingImpactSaveStore` (§7.4's persisted record), and the trigger/schedule/finalize/cancel/resume orchestration were all built into `IntervalRecorderService` — the same class that already owns `lockFiles()`/`unlockFiles()`/the rolling-buffer timer, so the new logic sits next to the exact mechanism it reuses rather than being injected in from outside. `ImpactDetectionSettings` was added to `AppSettings` now (mirroring `WatermarkSettings` in §5) rather than waiting for the rest of §11's settings additions, since `ImpactDetector` needs a real `enabled`/`postImpactDurationMinutes` to be genuinely wired.

**A real bug found and fixed along the way, load-bearing for this whole feature.** `deleteOldRecordings()`'s locked-range check was `Math.max(counter - timeMultiplier, lockedIndex ?: 0)`. Manual "Save" only ever holds a lock for the few seconds its own concatenation takes, so this never mattered in practice — but working through the arithmetic for a multi-*minute* hold (impact detection's whole premise) showed that `Math.max` only protects locked batches until the normal rolling window's natural earliest-to-keep catches up to the locked index, at which point `Math.max` picks the rolling window's (larger) value and **deletes straight through the lock** — the opposite of "protects all currently-retained batches... immediately" (§7.2 step 1). Fixed to `Math.min`, which correctly caps deletion at the locked index indefinitely, no matter how long the lock is held; this also incidentally closes a narrow pre-existing race in manual save itself (a cycle-timer tick landing mid-concatenation could previously have deleted a file out from under an in-progress read).

**Ordering fix in `VideoRecorderService.stop()`.** The natural place to "finalize a pending save if the user manually stops recording early" would be `IntervalRecorderService.stop()` — but `VideoRecorderService.stop()` calls `super.stop()` *before* it stops the actively-recording camera segment and waits for it to flush (`_videoFinalizerListener`). Finalizing that early would risk concatenating while the last batch file is still being written. This is exposed as a separate `finalizePendingImpactSaveOnStop()` method that `VideoRecorderService.stop()` calls explicitly, positioned after that flush-wait completes and before the camera closes.

**Auto-saved clips are marked via filename, not a database.** `BatchesFolder.getName()` gained an optional `tag` parameter; impact-triggered saves pass `BatchesFolder.AUTO_SAVED_FILENAME_TAG` ("auto"), producing e.g. `...-auto.mp4` instead of `....mp4`. The Recordings/Gallery screen (§9.2, a later phase) can key its "Auto-saved" badge off this suffix directly from the filename — no sidecar metadata file or database needed, and it survives the file being moved/exported/shared.

**A residual limitation, inherited from the broader rolling-buffer architecture, not fully closed here.** `IntervalRecorderService.counter` (used both as the batch-locking index and literally as each batch file's name) is a plain in-memory field — it resets to 0 if the service process is killed and restarted, which the persisted `PendingImpactSave.lockedIndex` correctly accounts for (restored directly via `restoreLock()`, not re-derived from the reset counter). But if recording continues long enough *after* such a restart for the counter to numerically climb back up to that old locked index, new batch files could collide by name with the still-protected old ones. For typical settings (≥10s intervals, the default 5-minute post-impact window), finalization completes long before that could happen, so this isn't a practical concern in the common case — but it's a real edge case a full fix would need to address by persisting `counter` itself across restarts, which is a materially bigger change to the whole recording architecture and out of scope for this feature specifically. Flagging it here rather than treating §7.4 as fully closed.

See the implementation note below for the storage-layer mechanics and why INTERNAL storage is exempt from this setting.

**Implementation notes.** The live preview closes a gap deliberately left open in §5's implementation: `VideoRecorderService` previously bound only `VideoCapture` (no `Preview` use case at all), so nothing was ever displayed from its camera session. A `Preview` use case (constructed eagerly, independent of when the camera actually opens, so a UI can hand it a surface provider at any time) is now bound into the same `UseCaseGroup` as `VideoCapture`, and the watermark `CameraEffect`'s targets were widened from `VIDEO_CAPTURE` alone to `VIDEO_CAPTURE or PREVIEW` — meaning the live preview shown during recording is composited from the exact same frames being encoded to disk, the actual WYSIWYG guarantee this section calls for. A new `RecordingPreview` composable (`ui/components/RecorderScreen/atoms/`) binds a `PreviewView` to this via `VideoRecorderService.setPreviewSurfaceProvider(...)`. This is deliberately separate from the pre-existing `CameraPreview.kt` (its own independent `Preview` use case + `ProcessCameraProvider` bind, Activity-lifecycle-owned, used only in the pre-recording preparation sheet where the service's camera isn't open yet and there's nothing to save yet anyway) — the two were not unified into one "always-open camera" architecture, since doing so would be a materially bigger change to the service's start/stop/pause/resume lifecycle than this phase's scope, and isn't needed for the WYSIWYG guarantee to hold (that only matters while actual encoding is happening).

The elapsed-time digit roller uses a per-character `AnimatedContent` with Inter's tabular figures (§8.2); the storage ring's fill fraction is deliberately based on "available space vs. the space needed for one full rolling-buffer window at the current retention setting" (the same reference point `LowStorageInfo`'s existing low-storage warning uses), not "used vs. total device capacity," since the latter is nearly meaningless on a modern phone and would just always read full. The pending-auto-save banner is wired end-to-end: `IntervalRecorderService.onPendingImpactSaveChange` → `VideoRecorderModel` (a new observed `pendingImpactSave` field, also read synchronously on reconnect) → the banner's Cancel button calls `cancelPendingImpactSave()` directly.

**Cut/Uncut state ownership.** The cut flag (`feedCut`) lives on `VideoRecorderService` — mirroring the existing `pendingImpactSave`/`onPendingImpactSaveChange` pattern (§7.3) already there — rather than on the generic `IntervalRecorderService<I, B>` base, since it's specific to this recorder and the PIP overlay (§9.5) needs to read it directly off the concrete service. `VideoRecorderModel` mirrors it as a Compose-observable, read synchronously on service (re)connect and kept in sync via a callback, the same way `pendingImpactSave` is mirrored there.

**Real-device bug found and fixed: the camera/preview never rotated with the device.** `MainActivity` declares `configChanges` (§10.1) specifically so it isn't recreated on rotation — but that also means CameraX's `Preview`/`VideoCapture` use cases, once bound, never got told about a new device rotation either (normally an Activity recreation is what implicitly refreshes this). CameraX's own docs are explicit that apps locking `configChanges` must call `setTargetRotation()` themselves. `VideoRecorderService` now registers a `DisplayManager.DisplayListener` and calls `preview.targetRotation = rotation` / `videoCapture.targetRotation = rotation` both once at camera-open time and on every subsequent rotation change. This is also *why* the watermark corner/orientation bug above happened: `WatermarkRenderer`'s compensation reads `frame.rotationDegrees`, which is derived from this same CameraX state — once CameraX itself had stale rotation info, the watermark's compensation was working from a wrong input regardless of its own sign bug. Both had to be fixed together.

**Three more real-device bugs found and fixed, all in the Cut/Uncut work above.**
1. **Cutting the feed didn't actually stop the camera preview, and camera content still showed at the screen edges.** The first version just drew an opaque black `Box` on top of a `RecordingPreview` that stayed mounted and bound underneath — the preview kept consuming frames and compositing them into its `PreviewView` the whole time, exactly the resource cost cutting the feed is supposed to avoid, and on-device this showed as camera content visibly bleeding through at the edges instead of a clean black screen. Fixed by conditionally composing `RecordingPreview` at all — `if (feedCut) { black screen + label } else { RecordingPreview(...) }` — so cutting the feed now actually removes the `PreviewView`, which triggers `RecordingPreview`'s own `DisposableEffect` to call `clearPreviewSurfaceProvider(...)` on the service, genuinely detaching the `Preview` use case from a surface rather than merely hiding a still-live one. Recording is unaffected either way, for the same "`VideoCapture` is bound independently" reason as always.
2. **The 4-button control row looked uneven once Cut/Uncut was added.** The row's original layout (from when it only had 3 buttons) centered the two edge buttons within their own half of the row via `weight(1f)`, with the middle buttons packed together with no gap — fine for exactly one middle button, but with two middle buttons of visibly different sizes (Pause's `FloatingActionButton` vs. CutFeed's 48dp square) it read as lopsided: Pause and CutFeed touching in the center, Delete/Save floating in comparatively large empty half-widths. Fixed by switching the whole row to `Arrangement.spacedBy(20.dp, Alignment.CenterHorizontally)` with no per-button `weight()` — a fixed gap between every button reads as balanced regardless of any single button's own size, which a "centered in half the available space" layout doesn't guarantee once there's more than one button of a different size in the mix.
3. **The live preview could freeze on its last frame after resuming from the PIP overlay and switching back to full-screen.** Fixing #1 above (making `RecordingPreview` conditionally composed) surfaced a deeper, pre-existing single-owner problem: the service's `Preview` use case only ever has ONE active surface provider, but the Activity's own `RecordingPreview` and the PIP overlay's `RecordingPreview` (§9.5) are two independent instances of the exact same composable that can both want it, with no guaranteed order between one detaching and the other attaching. Concretely: opening the PIP overlay hands it the surface-provider slot (silently displacing the Activity's, which never re-attaches on its own since its one-time `AndroidView` factory already ran); closing the PIP later just nulls the slot outright, and nothing ever re-attaches the Activity's preview to reclaim it, since Compose only re-runs `AndroidView`'s factory on first mount, not on every recomposition — leaving the Activity's `PreviewView` permanently starved of new frames, frozen on whatever it last displayed. Fixed on both sides: (a) `VideoRecorderService.setPreviewSurfaceProvider`/new `clearPreviewSurfaceProvider` now track the active provider **by identity**, so a stale/late clear from a composable that's since been superseded by a different one can never wipe out that newer one; (b) `RecordingPreview` now also re-attaches its own captured surface provider on every `Lifecycle.Event.ON_RESUME` of its `LocalLifecycleOwner`, not just once at creation — so the Activity's own preview actively reclaims the slot the moment the app returns to the foreground, rather than passively waiting for a hand-off that was never coming.
4. **The cut-feed placeholder read "Dashcam active" even while the recording was also paused**, on both the Record screen and the PIP overlay (§9.5) — the label was wired to `feedCut` alone with no `isPaused` check, so a driver looking at the black placeholder had no way to tell "recording, just not shown" apart from "not actually recording right now" — the one distinction that label exists to make. Fixed by branching the string itself on `isPaused` in both places (`ui_recorder_feedCut_activeLabel` vs. the new `ui_recorder_feedCut_pausedLabel`), rather than introducing a third visual state — the black background and layout stay identical, only the word changes.
5. **In landscape, the last button in the 4-button column could end up off-screen/invisible.** The column stacked all 4 buttons one-per-line (Save, Pause, CutFeed, Delete) with 16dp gaps — a total height of roughly Save's 48dp + Pause's ~56dp FAB + CutFeed's 48dp + Delete's 48dp + 3×16dp gaps ≈ 248dp, which can exceed the available height in landscape (the device's short axis), pushing Delete (the last button) past the bottom of whatever panel hosts this control row — a real reported bug, not something that showed up in portrait where the row lays out horizontally instead. Fixed by arranging the 4 buttons as a 2x2 square (Save+Pause on top, CutFeed+Delete below) instead of a single column — roughly halving the total height regardless of how tall the hosting panel is allowed to get, while keeping the same relative reading order.

**A related product decision, not a bug: the PIP overlay's show conditions no longer exclude a cut feed.** Originally (§9.5 as first written) cutting the feed was one of the overlay's *hide* conditions — the reasoning being "don't show camera content in the overlay if the user's chosen not to see it on the main screen either." Explicit follow-up direction reversed this: the overlay should still appear while backgrounded even if the feed is cut, just showing its own "Dashcam active" placeholder (mirroring the Record screen's, §9.1) instead of live video — losing access to the overlay's Pause/Resume and tap-to-reopen controls just because the feed happens to be cut isn't the behavior wanted. `feedCut` is now Compose-observable on the service (split into a private `_feedCut` delegate + a public getter-only `feedCut`, to avoid a real "platform declaration clash" compile error between the delegated property's own synthetic setter and the hand-written `setFeedCut` function), and `PipOverlayContent` reads it directly to pick between its live-preview and "Dashcam active" branches, the same way it already picks between live and paused.

**"Process Video" implementation notes.** The rolling-buffer chunks and the final saved output already share one important architectural fact for CUSTOM/MEDIA storage that this feature leans on directly: raw in-progress chunks live in a private staging subfolder (`BatchesFolder.subfolderName`, e.g. `customFolder/.recordings/` for a SAF tree, or a `.video_recordings`-tagged MediaStore path for MEDIA) *inside* the same location the user picked, while a normal (processed) save writes its single merged file one level up, directly into that location's root (`customFolder` itself, or the MediaStore path one segment shorter) — `BatchesFolder.getConcatenationDestination()` already encodes exactly this split. With "Process Video" off, `BatchesFolder.moveChunksToDestination()` (new) reuses that same `getConcatenationDestination()` per chunk — generating one destination per source file (`getName(date, ext, tag = "$outputTag-chunk$NNN")` instead of one shared output name) — so "moving chunks to the main save folder" is literally relocating them from that staging subfolder up into the root, the same journey a concatenated file already takes, just without the merge step in between. No new retention logic was needed: `moveChunksToDestination()` reuses the exact same `getBatchesForConcatenation()` file selection `concatenate()` already relies on, and by the time either runs, `deleteOldRecordings()`'s existing rolling-window pruning (`maxDuration`/`intervalDuration`, §7.5-adjacent) has already limited what's available to move to the currently-retained window — there's nothing left to compute. Each chunk is relocated via a plain stream copy (source → destination, both already resolved through the exact same per-backend APIs `concatenate()` uses) followed by deleting the source — a real move, not a duplicate; this happens per-file rather than as a final bulk wipe specifically so a concurrent dual-recording secondary stream's own not-yet-processed chunks are never at risk of being swept up by a blanket delete. **INTERNAL storage is deliberately exempt** — `RecorderEventsHandler.saveRecording()`'s only INTERNAL exit path is `saveVideoFile()`, a single-file SAF "save as" picker; prompting it once per chunk would be a jarring multi-dialog UX for what might be a dozen files, so INTERNAL always concatenates regardless of this setting (checked via `batchesFolder.type != BatchType.INTERNAL` at both of this feature's two call sites — the Record screen's Save button, and `IntervalRecorderService.concatenateCurrentBuffer()`, shared by the PIP overlay's Save button and impact auto-save). One asymmetry worth noting: the Record screen's Save button reads `processVideo` from live settings (so a mid-recording toggle takes effect on the very next tap), while the PIP/auto-save path reads it from the service's frozen settings snapshot — the same "next recording session" limitation every other `VideoRecorderSettings` field already has (§16 item 3-adjacent), not a new one introduced here.

**Real bug found and fixed: tapping Save stopped the recording even with "Process Video" off.** The Save button's two gestures (§8.2/`SaveButton`'s own doc comment) are hardcoded to fixed roles — tap = save-and-stop (the button's primary, no-confirmation action), long-press = save-current-without-stopping (behind a confirmation sheet, since it's an easy gesture to trigger by accident). That mapping was left unconditional when "Process Video" was added, so turning it off — meant for a continuously-running rolling buffer the user repeatedly saves chunks out of, exactly why Delete was also removed above — still ended the recording on every single tap, the same as the default case. Fixed in `_PrimitiveControls` (`VideoRecordingStatus.kt`) by swapping which action each gesture triggers when `!uiState.processVideo`: tap now calls `actions.onConfirmSaveCurrent` directly (no confirmation sheet — it's the expected, low-friction action in this mode) and long-press now calls `actions.onSaveAndStop` directly (also no confirmation sheet, since the deliberate gesture itself is already the safeguard) — recording keeps running after a tap, and stopping is still reachable, just no longer the easy gesture. The PIP overlay's own Save button (§9.5) never had this bug — it was built from the start to call `saveCurrentBufferNow()` directly, which never stops recording regardless of this setting.

**A second real bug found and fixed, exposed by the swap immediately above: a quick tap-then-long-press on Save crashed into the recorder error dialog with "Process Video" off.** Once tap and long-press both fire real save actions with no confirmation gating either (previous bug's fix), nothing stopped a user from triggering both in quick succession — and `RecorderEventsHandler.saveRecording()` had no protection against two overlapping invocations to begin with, on either gesture, in either mode. With "Process Video" on this was merely wasteful (`concatenate()` doesn't delete its source batches, so two concurrent calls just produced two redundant output files from the same still-intact inputs). With it off, `moveChunksToDestination()` deletes each source chunk immediately after moving it — so a second, concurrent `saveRecording()` call reading its own `getBatchesForConcatenation()` snapshot could pick up a chunk the first call had already moved-and-deleted by the time it tried to open it, throwing a `FileNotFoundException` that surfaced as `showRecorderError`. Fixed with a new `isSaving` flag, set synchronously the instant `saveRecording()` starts and checked at its very top (a second call while one is in flight returns an already-completed no-op `CompletableDeferred` instead of starting a race) — deliberately distinct from the existing `isProcessing` flag, which only flips true after a 250ms delay (to avoid flashing a dialog for fast saves) and so can't guard against a second trigger landing inside that same 250ms window, exactly where this bug's repro (short tap immediately followed by a long-press) landed.

**A third real bug, the actual full explanation: the error reproduced even with the two taps seconds apart, well outside any concurrency window** — so `isSaving` above, while a genuine fix for genuinely-overlapping saves, wasn't the whole story. `getBatchesForConcatenation()`/`moveChunksToDestination()` never excluded the segment CURRENTLY open for writing from what they select — `concatenate()` tolerates this fine (it only reads its inputs, so including the live segment merely risks a slightly-truncated tail in the merged output, never a hard error), but `moveChunksToDestination()` deletes each source after moving it. Concretely: tapping Save (short tap → save-current in this mode) calls `startNewCycle()` first, which immediately creates a new, empty, actively-recording segment file on disk before the save's background thread even runs — that brand-new segment was getting swept into "chunks to move," moved out, and deleted while the camera pipeline was still actively writing frames into it. The delete-of-a-still-open-file itself doesn't fail immediately (POSIX allows writes to continue against an already-unlinked file descriptor), so nothing appeared wrong until *later* — when the long-press's `stopRecording()` tried to properly finalize that exact segment (moments to seconds afterward, matching the reported "5 seconds later" repro) and failed, since the file it expected to still be there on disk was gone. Fixed with a new `excludeActiveChunk: Boolean` parameter on `moveChunksToDestination()`: when true, the highest-counter chunk (guaranteed to be the currently-open one, since `getBatchesForConcatenationWithCounter()` — the counter-preserving sibling of `getBatchesForConcatenation()` added alongside this fix — sorts ascending) is dropped before anything is moved. Passed as `true` unconditionally from `IntervalRecorderService.concatenateCurrentBuffer()` (impact auto-save and the PIP's Save button never stop recording, so there's always an active segment to protect), and as `recorder.isCurrentlyActivelyRecording` from `RecorderEventsHandler.saveRecording()` (true only for "Save Current," where recording continues — false for "Save & Stop," where `stopRecording()` has already finalized every segment before this runs, leaving nothing left to exclude). A related, adjacent bug fixed in the same pass: chunk destination filenames were tagged with a call-local index (`chunk001`, `chunk002`, ...) that restarted at 1 on every save — so a second save within the same recording session (exactly what this mode is for) silently overwrote the first save's chunk files with the second save's. Fixed by tagging each chunk with its own permanent, ever-increasing counter (also now threaded through by `getBatchesForConcatenationWithCounter()`) instead, which is unique for the lifetime of the whole recording session.

### 9.5 PIP overlay window (backgrounded recording)

A 160×90dp draggable floating window — live preview plus Pause/Resume, Cut/Uncut, and Save buttons, no elapsed time, no Stop/Return button — shown via `WindowManager` when the app is backgrounded while a recording is actively in progress and the PIP setting (§9.3/§11) is on. Recording itself is entirely unaffected: it continues in the foreground service regardless of whether the overlay is showing, exactly as it already does when merely backgrounded with no overlay at all (§10.2). Tapping anywhere on the window background (not any button) reopens `MainActivity` in the foreground — the fastest way back into the full app from the overlay, without needing to hunt for the app icon or the foreground notification.

**Show conditions** (re-checked fresh every time the app goes to the background, not cached — any of them can change between one backgrounding and the next):
1. A recording is actively in progress (not paused) at the moment of backgrounding.
2. The PIP setting is on (§9.3/§11).
3. `Settings.canDrawOverlays()` — the special permission is actually granted.
4. The overlay isn't already shown.

Deliberately does **not** gate on the feed being cut (§9.1) — see the implementation note below for why that changed from the original design.

**Hide conditions:** the app returns to the foreground; the recording fully stops. Pausing does **not** hide it — the window stays mounted and its content swaps to a dark, paused placeholder with a Resume button; only a full stop tears it down, since there's no "resume from the overlay" path back once recording has actually stopped.

**Screen-off hibernation (energy-efficiency pass).** The overlay keeps a full live GPU-composited camera preview running via `WindowManager` for as long as it's showing — including, previously, while the phone's screen was off, when nothing could possibly see it. `ProcessLifecycleOwner` alone doesn't catch this: once the app is already backgrounded (and the overlay already showing), the screen turning off/on doesn't start/stop any of the app's own activities, so no further `onStop`/`onStart` fires from that alone. Fixed with a dedicated, dynamically-registered `BroadcastReceiver` for `Intent.ACTION_SCREEN_OFF`/`ACTION_SCREEN_ON` in `VideoRecorderService` (registered/unregistered alongside the `ProcessLifecycleOwner` observer in `onCreate`/`onDestroy`, via `ContextCompat.registerReceiver(..., RECEIVER_NOT_EXPORTED)` since these are system-only broadcasts) — `SCREEN_OFF` calls the same `hidePipOverlay()`, `SCREEN_ON` calls the same `maybeShowPipOverlay()`, the existing show/hide functions above already used for the foreground/background transition. No new teardown path, just an additional trigger for the existing one. (`SCREEN_OFF`/`SCREEN_ON` are explicitly exempted from the API 26+ implicit-broadcast restrictions — they're only ever deliverable to a dynamically-registered receiver in the first place, so this can never move to a manifest entry.)

**Hosting.** The overlay has to be hosted from the recording *service*, not `MainActivity` — the Activity can be destroyed when the user swipes the app away, but the foreground service keeps running. `VideoRecorderService` observes `ProcessLifecycleOwner` (via the `androidx.lifecycle:lifecycle-process` dependency, §13) rather than its own `LifecycleOwner`: the service's own lifecycle (already available via `LifecycleService`) tracks the *service's* create/destroy, not the *app's* foreground/background state, which is what the show/hide conditions above actually need. `onStop` (app backgrounded) triggers the show check and (energy-efficiency pass) also calls `RecorderService.onAppBackgrounded()`, which stops the once-a-second elapsed-time UI timer (`recordingTimeTimer`) — nothing needs it ticking with no foreground UI to observe it, since the recording notification renders its own chronometer from a single timestamp rather than from these ticks. `onStart` (app foregrounded) hides the overlay and calls `onAppForegrounded()`, which adds the elapsed backgrounded duration to `recordingTime` in one step and restarts the timer, rather than relying on ticks that were deliberately skipped. This interacts correctly with an explicit pause/resume (e.g. via the overlay's own buttons) happening while still backgrounded — `RecorderService.pause()`/`resume()` now flush or (re)start that same backgrounded-duration tracking, so elapsed recording time never double-counts or drops time across an in-background pause/resume.

Hosting a bare `ComposeView` outside any Activity/Fragment needs a `LifecycleOwner`, `ViewModelStoreOwner`, and `SavedStateRegistryOwner` to attach it to — `VideoRecorderService` gets the first for free from `LifecycleService`, and now also implements the other two itself. Neither the `ViewModelStore` nor the `SavedStateRegistry` is used for anything real (there are no ViewModels in the overlay, and nothing worth restoring across process death) — this is the minimal plumbing Compose requires to attach at all outside an Activity.

**Window + drag + tap-to-open.** The window is `WindowManager.LayoutParams(TYPE_APPLICATION_OVERLAY, FLAG_NOT_FOCUSABLE or FLAG_LAYOUT_NO_LIMITS, ...)` at a fixed 160×90dp (16:9), `addView`/`updateViewLayout`/`removeView` all wrapped defensively — an OEM-specific overlay restriction failing here must never risk the actual recording, only the optional floating window. The entire window background does double duty as the drag handle *and* the "reopen the app" tap target (there's no dedicated drag-handle strip or separate tap zone; at this size every pixel matters) — two sibling `pointerInput` blocks, one running `detectTapGestures` and one running `detectDragGestures`, rather than trying to fold both into a single detector. This works because `detectDragGestures` only consumes a pointer event once the touch-slop threshold is actually exceeded — a plain tap's down/up passes through unconsumed, so the sibling `detectTapGestures` block still sees and completes it as a genuine tap; an actual drag consumes the movement instead, which cancels the pending tap detection automatically. Reopening the app sends an `Intent(context, MainActivity::class.java)` with `FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_REORDER_TO_FRONT` — `NEW_TASK` is required to start an Activity from a Service context at all, and `REORDER_TO_FRONT` brings the existing `MainActivity` instance already in its task back to the front instead of stacking a redundant new instance on top of it (`MainActivity` uses the default `standard` launch mode, so a bare `NEW_TASK` alone would create a fresh instance every tap). The overlay isn't explicitly hidden from the tap handler itself — that's left to the existing `ProcessLifecycleOwner.onStart` → `hidePipOverlay()` path once the app actually reaches the foreground, so there's only one place that ever tears the overlay down, not two racing each other. The button row (below) sits on top of both gesture detectors and consumes its own pointer events first, so tapping a button never starts a drag or reopens the app (standard Compose nested-pointer-input dispatch — no extra coordination code needed).

**Content.** The live preview stays mounted for the overlay's entire lifetime *while the feed isn't cut*, reusing the same `RecordingPreview` atom the Record screen uses (§9.1) bound to the service's own `Preview` use case — while paused, a dark scrim and dimmed pause icon simply draw on top of it rather than unmounting it. This means the preview's surface-provider attach/detach happens once when the overlay is shown/hidden, not on every pause/resume toggle inside it, and it's simpler than it sounds: "no camera use while paused" is already guaranteed independently by `VideoRecorderService.pause()`'s existing `closeCamera()` call (§9.1), regardless of what's drawn in the overlay. If the feed IS cut, `RecordingPreview` isn't composed at all — a black screen with a "Dashcam active"/"Dashcam paused" label (picked the same way as the Record screen's own cut placeholder, §9.1's bug note #4 — whichever is accurate depending on `isPaused`, since the overlay can be cut and paused independently of each other) takes its place instead, mirroring the Record screen's own cut placeholder and for the same reason (actually detaching the surface provider, not just painting over a still-live preview) — plus a thin 1dp border, in the user's configured accent color (matching the buttons, via the same `RoadLogTheme` wrapping), around the entire window, since a small black rectangle floating over an arbitrary background (whatever app the user's actually looking at) otherwise has no edge of its own to distinguish it from what's behind it once there's no live video filling it.

Three 32dp circular icon buttons (24dp glyphs — the button row's original sizing, restored once the sizing below no longer had to compensate for a touch-target bug) — Pause/Resume, then Cut/Uncut, then Save, the same relative order as the Record screen's own control row (§9.1: Pause, CutFeed, ..., Save last) — sit in a `Row` anchored `Alignment.BottomCenter`, `Arrangement.spacedBy(10.dp, Alignment.CenterHorizontally)` (tightened from 12dp to fit a third button inside the fixed 160dp width with comfortable side margins): bottom-aligned, evenly spaced, and centered as a group, rather than the single button pinned to a bottom corner this section originally specced (before there was a second, then third, button to arrange). Pause/Resume and Cut/Uncut call straight through to the service (`pauseRecording()`/`resumeRecording()`, `setFeedCut()`) — no broadcast/receiver indirection needed, since the overlay is hosted from the service's own context — and all three stay available regardless of the others' state (e.g. Save works the same whether paused, cut, or neither). Swapping between live/paused/cut content, and each button's own icon/label, is a plain Compose recomposition off service-owned observable flags, not routed through the same callback the Activity-side UI uses for its own state (that slot is already claimed — see the implementation note below).

**Save button.** Unlike the Record screen's own Save button (§9.1), which routes through `RecorderEventsHandler`/`VideoRecorderModel.onRecordingSave` — a callback wired from the Activity's Compose tree, not reachable from a service-hosted overlay — the PIP's Save button calls a new self-contained `IntervalRecorderService.saveCurrentBufferNow()` directly. This factors out and reuses the same concatenate logic `finalizePendingImpactSave()` (§7.5) already uses for impact auto-save (extracted into a shared private `concatenateCurrentBuffer(tag)` helper, called with `BatchesFolder.AUTO_SAVED_FILENAME_TAG` for impact saves and with no tag — a plain save, same as the Record screen's own — for the PIP's manual one), so it needs nothing beyond what the service already owns (`batchesFolder`, `settings`, `getRecordingInformation()`). It calls `startNewCycle()` first, synchronously, before launching the concatenation on `Dispatchers.IO` — the segment still actively being written has to be flushed to its own completed file first, or the last (still in-progress) interval of footage would be silently missed from what gets concatenated. No success/failure snackbar is shown (there's no `SnackbarHostState` reachable from the service either) — matching the same no-feedback precedent already accepted for impact auto-save.

Each button is a plain `Box` + `clickable` (§8.2's own convention for the Record screen's small buttons — `CutFeedButton`/`DeleteButton`/`SaveButton` — not Material3's `IconButton`), deliberately: `IconButton` pads its content out to a minimum 48dp touch target via `minimumInteractiveComponentSize()`, invisibly, regardless of the visual size an explicit `Modifier.size()` draws. At a smaller button size tried in an intermediate pass (down to 18dp, while chasing a visually tighter fit), that invisible inflation was large enough for the two buttons' actual tap targets to overlap even with their drawn circles clearly separated by the `Row`'s 12dp gap — a real, on-device-reported bug, fixed by switching to the raw-`Box` pattern, whose layout bounds are exactly the size specified with no hidden padding, so the `Row`'s gap is genuinely the entire gap between tap targets, not just between visible pixels. With that fixed, the button size itself no longer needed to shrink to avoid overlap, so it was restored to the button row's original 32dp/24dp (button/glyph) sizing.

**Implementation notes.** The paused/live swap is driven by a small Compose-observable flag on `VideoRecorderService` itself, set directly in `pause()`/`resume()`/`start()`, rather than piggybacking on the service's existing `onStateChange` callback — that callback is a single nullable slot already claimed by `VideoRecorderModel` for the Activity-side UI (§2.1's port table), and a second assignment from within the service would just overwrite (or be overwritten by) it depending on ordering. Keeping the overlay's own state self-contained avoids that conflict entirely. `feedCut` (§9.1) is read the same way — directly off the service, Compose-observable — but unlike `overlayIsPaused`, `feedCut` already had a hand-written `setFeedCut` function before this overlay existed, which meant `var feedCut by mutableStateOf(false) private set` didn't compile: a delegated property's private setter still needs a real JVM accessor method (unlike a plain `var`'s, which the compiler can elide), and the synthetic `setFeedCut(Boolean)` that generates collides — a "platform declaration clash" — with the hand-written one. Fixed by splitting it into a private `_feedCut` delegate plus a public getter-only `feedCut` property, with `setFeedCut` writing through to `_feedCut` — the standard pattern for exactly this "want a delegated backing property AND a custom-named mutator" combination.

**A real bug found and fixed: the overlay's buttons ignored the user's configured accent color.** `PipOverlayContent`'s `MaterialTheme.colorScheme.primary` reads were silently resolving to Compose's default, unbranded color scheme rather than `AppSettings.accentColorArgb` — because, unlike every other screen in the app, this `ComposeView` is hosted directly on `WindowManager` (§9.5) with no `MainActivity` ancestor to supply `RoadLogTheme`'s `MaterialTheme` the normal way (§8.2). Fixed by wrapping `PipOverlayContent`'s own content in `RoadLogTheme(amoled = ..., accentColor = ...)`, reading both straight off `recorderService.settings` — the same plain settings snapshot the rest of the service already relies on (e.g. `WatermarkOverlay`'s `getSettings` lambda), refreshed only when a recording (re)starts rather than on every live settings change. That's a pre-existing, accepted limitation shared by every other in-service settings consumer, not a new one introduced here — a mid-recording accent-color change wouldn't reach the watermark either.

**A real, more severe bug that fix immediately introduced: the app crashed the instant the overlay tried to appear.** `RoadLogTheme` (§8.2) has always assumed an Activity-hosted caller — its `SideEffect` block does `(view.context as Activity).window` to set the navigation-bar color and status/nav-bar icon appearance, which is exactly correct for `MainActivity` but was never exercised against any other kind of host before now. Wrapping `PipOverlayContent` in `RoadLogTheme` (the fix immediately above) meant that cast now ran against the PIP's `ComposeView`, whose `context` is the recording service's, not an `Activity` — an unconditional `ClassCastException` on every single attempt to show the overlay, thrown during composition setup, before anything was ever drawn to screen (matching the reported symptom exactly: a crash on backgrounding, before the PIP became visible). Fixed by changing the cast to `as?` and skipping the window-styling side effect entirely when there's no `Activity` to style — a non-Activity host (the PIP, or any future one) still gets `RoadLogTheme`'s color scheme/typography/shapes, just without touching system-bar chrome that doesn't apply to it. `MainActivity`'s own use of `RoadLogTheme` is unaffected — it still finds a real `Activity` and gets the same window styling as before.

**A related product decision, not a bug: the PIP overlay's show conditions no longer exclude a cut feed.** The original design (as first specced) treated a cut feed as one of the overlay's *hide* conditions, reasoning "don't show camera content in the overlay if the user's chosen not to see it on the main screen either." Explicit follow-up direction reversed this: losing the overlay's Pause/Resume and tap-to-reopen controls just because the feed happens to be cut isn't the wanted behavior — the overlay should still appear while backgrounded even with the feed cut, just showing its own "Dashcam active" placeholder instead of live video, per the Content note above.

**Real bug found and fixed (compile-time).** The first version of the `ViewTree*Owner` wiring above used the classic `ViewTreeLifecycleOwner.set(view, owner)` / `ViewTreeViewModelStoreOwner.set(view, owner)` / `ViewTreeSavedStateRegistryOwner.set(view, owner)` static calls that most existing documentation and blog posts still show. This fails to compile — `Unresolved reference` — against the `androidx.lifecycle`/`androidx.savedstate` versions this project actually resolves (confirmed by decompiling the exact `.aar`s Gradle resolves for this module, not just checking that a same-named class exists somewhere in a shared machine-wide Gradle cache, which is what a first, wrong diagnosis relied on). As of these versions, those static `.set()` methods are hidden from Kotlin source resolution (binary-compatible but Kotlin-invisible) in favor of Kotlin extension functions of a different name, compiled into the same class file: `View.setViewTreeLifecycleOwner(owner)`, `View.setViewTreeViewModelStoreOwner(owner)`, `View.setViewTreeSavedStateRegistryOwner(owner)`. Fixed by switching to the extension-function form — no `build.gradle` change needed, since all three artifacts were already transitively resolved; this was purely an API-surface correction.

**Two real-device bugs found and fixed, both crashing the app on every tap of Start (not gated by the PIP setting at all — both fire during service creation, before any PIP-specific gating logic ever runs).**
1. `VideoRecorderService.onCreate()` called `super.onCreate()` — which dispatches `ON_CREATE` and advances the service's `Lifecycle` from `INITIALIZED` to `CREATED` — before calling `savedStateRegistryController.performAttach()`/`performRestore(null)`. Both of those assert the owner's lifecycle is still `INITIALIZED` and throw `IllegalStateException` otherwise. Fixed by moving the `performAttach()`/`performRestore(null)` calls to run first, before `super.onCreate()`.
2. `pipOverlay` was a plain field initializer (`private val pipOverlay = PipOverlayWindow(this)`), and `PipOverlayWindow`'s constructor immediately calls `context.getSystemService(WindowManager::class.java)`. Field initializers run inside the Kotlin constructor, which Android invokes via reflection (`newInstance()`) *before* `attachBaseContext()` gives the Service a real `Context` — calling `getSystemService()` on `this` at that point throws a `NullPointerException` on the still-null base context. This is exactly the trap `displayManager` already sidesteps elsewhere in this file with `by lazy`; `pipOverlay` needed the same treatment and didn't get it in the first pass. Fixed by making it `private val pipOverlay by lazy { PipOverlayWindow(this) }`, deferring construction to first actual use (`maybeShowPipOverlay()`/`hidePipOverlay()`), well after the service is attached.

Both were caught via real-device testing after the compile-clean build above turned out not to be sufficient — a clean `assembleDebug` only proves the code compiles, not that service construction/lifecycle ordering is correct at runtime, and this section's own `ViewTree*Owner`/`SavedStateRegistryController` wiring is exactly the kind of "novel for this codebase" territory §9.5 already flagged as risk before either bug was found.

**Needs on-device confirmation** (no camera-equipped device/emulator available in this environment, consistent with every other section's caveat, §15): the overlay actually appearing/disappearing correctly across real background/foreground transitions on a real launcher, not just the gating logic being correct in source; drag responsiveness and whether per-delta `updateViewLayout` calls are smooth enough in practice; that tapping the background reliably reopens the app without ever being swallowed as a micro-drag (or, conversely, that a real drag never accidentally reopens the app) — the tap/drag disambiguation was reasoned through against `detectDragGestures`' actual slop/consumption behavior, not observed on a touchscreen; that the identity-tracked surface-provider hand-off between the overlay's `RecordingPreview` and the Activity-side one (§9.1's real-device fix for the frozen-preview bug) is genuinely race-proof across real background/foreground timing, not just in the two orderings reasoned through on paper; whether the brief window where recording state flips back to "recording" on Resume before the camera has actually finished reopening produces any visible glitch in the swapped-back live preview; and OEM-specific overlay-permission/behavior variance (the defensive `runCatching` wrapping around the `WindowManager` calls is a safety net for this, not a substitute for testing it).

## 9.6 Energy & Compute Efficiency (opt-in features)

A dedicated pass beyond the whole-module performance refactor (§16, item covering Stage 0-4): that work eliminated wasted CPU cycles (recomposition, threading, redundant DataStore subscriptions); this one targets the app's actual *power draw as a dashcam device* — a phone mounted on a windshield, typically recording continuously for hours. §5.5 (Silent Watermark GPU/GPS teardown) and §9.5 (PIP screen-off hibernation, presence-gated recording timer) cover the always-on, no-setting fixes from this same investigation. This section covers the four opt-in-setting features from the same pass, each following the existing `VideoRecorderSettings`/`PipSettings`-style schema addition and `ui/components/SettingsScreen/Tiles/*Tile.kt` Switch pattern.

**PIP idle-timeout suspension** (`PipSettings.idleSuspendEnabled`, default on). Complements §9.5's screen-off hibernation for the screen-on-but-ignored case: a new `VideoRecorderService._pipIdleSuspended` flag (Compose-observable, mirroring `feedCut`'s pattern) driven by `resetPipActivity()`/`cancelPipIdleSuspend()` — a coroutine restarted on every drag/tap/button press (wired into `PipOverlayContent.kt`'s existing `pointerInput` blocks and each `PipButton.onClick`) that, left uninterrupted for `PIP_IDLE_SUSPEND_TIMEOUT` (20s), sets the flag. `PipOverlayContent` ORs it with the existing `isCut` (`showPlaceholder = isCut || isIdleSuspended`) at the exact point that already conditionally composes `RecordingPreview` — reusing the already-hardened surface-provider teardown path from the manual Cut/Uncut feature, not a new one, so idle suspension gets the same real GPU-compositing-stop that Cut/Uncut already achieves, not just a painted-over placeholder.

**Adaptive display dimming while recording** (`AppSettings.dimScreenWhileRecording`, default **off** — a real, visible behavior change to a screen users may rely on glancing at, worth defaulting on only after real-device validation). `KeepScreenOn()` (`ui/utils/views.kt`) only ever defeats the screen-off timeout — zero brightness control. New `Modifier.dimWhileRecording(enabled, idleTimeoutMs)` composable extension alongside it: sets the hosting Activity's `Window.attributes.screenBrightness` (a **per-window** override, not the system-wide `Settings.System.SCREEN_BRIGHTNESS`, which would need `WRITE_SETTINGS` and affect every other app) down to `MIN_SCREEN_BRIGHTNESS` (0.02f, not fully 0 — some panels render pure-0 as unreadable black) after 15s of no touch, restoring instantly on the next one. Detects touches via a non-consuming `pointerInput` observer at `PointerEventPass.Initial` on the Record screen's outermost `BoxWithConstraints`, so it never steals or blocks input meant for the buttons/preview underneath. The dim timer's own delay doubles as the "don't dim immediately after recording starts" grace period, since `lastActivityAt` starts at composition time — no separate initial-delay mechanism needed.

**Hardware-encoder guardrail** (`AppSettings.softwareEncoderDetected`, advisory-only, no setting to toggle — it's a detected condition, not a preference). Encoding is fully delegated to CameraX/Camera2 defaults with no app-level visibility into whether a *hardware* (vs. much more power-hungry software/CPU) encoder actually got resolved for the selected quality. New `helpers/EncoderCapabilityChecker.isHardwareEncoder(cameraInfo, quality)`: `QualitySelector.getResolution(cameraInfo, quality)` (a real, documented CameraX static API — verified against the current public API surface before use) gives the actual resolved width/height for the quality; `MediaFormat.createVideoFormat("video/avc", w, h)` + `MediaCodecList(REGULAR_CODECS).findEncoderForFormat(...)` resolves the same encoder the OS would actually pick (CameraX's `Recorder` defaults to H.264/AVC unless a `VideoEncoderConfig` requests otherwise, which this app never does); `MediaCodecInfo.isHardwareAccelerated()` (API 29+) or a name-prefix heuristic (`OMX.google.*`/`c2.android.*` = software, pre-29) makes the call. `VideoRecorderService.checkEncoderCapability()` runs this off-thread right after camera bind (alongside `applyFocusSettings()`) and persists the result via DataStore every time (re-evaluated per camera-open, never permanently sticky). Ships as a one-time dismissible Settings banner only — deliberately **not** an auto-fallback to a lower quality, since silently changing what the user configured is a bigger trust issue for a dashcam than for a generic camera app.

**Lightweight secondary-stream profile for dual recording** (`VideoRecorderSettings.useLightweightSecondaryStream`, default **on**). Dual (front+back) recording previously bound both cameras at identical quality/bitrate/frame-rate — two concurrent hardware-encoder instances at full quality, often two simultaneous 4K encodes, for a secondary stream whose only job is verifying who was in the driver's seat, not evidentiary road footage. `buildRecorder()`/`buildVideoCapture()` (`VideoRecorderService.kt`) now take a `useLightweightSecondaryStreamProfile` parameter; when true (the secondary-stream call site, gated on the new setting), they use fixed constants (`SECONDARY_STREAM_QUALITY = Quality.SD`, `_BITRATE = 2_000_000`, `_FRAME_RATE = 15`) instead of cloning `settings.videoRecorderSettings`, roughly halving dual recording's total concurrent encode cost. A plain boolean + fixed preset was chosen over a full parallel `SecondaryStreamSettings` schema (quality/bitrate/frame-rate all independently configurable) to keep the feature's scope proportional to how rarely dual recording is actually used — turning the setting off restores the original symmetric-quality behavior exactly.

**Not implemented from the same investigation's brainstorm, and why:** a motion-triggered ("livestream-style") adaptive bitrate boost on sudden speed change was investigated and explicitly declined — CameraX's `Recorder` has no live bitrate/quality API (confirmed against CameraX 1.5's Nov 2025 release notes), true seamless adaptation would require abandoning `Recorder` for a hand-rolled Camera2+MediaCodec+MediaMuxer pipeline (the exact rearchitecture §5.1 already rejected for unrelated reasons), the only buildable approximation causes a real recording gap, it wouldn't reduce battery drain versus simply defaulting to a lower fixed quality, and the trigger condition (sudden speed change) is exactly the moment continuous footage matters most — reconfiguring the encoder right then risks losing the moment the boost was meant to capture. A broader thermal/battery/OS-Battery-Saver-driven adaptive quality governor was also scoped (reusing `pause()`/`resume()`'s close→rebuild→reopen cycle) but held back as a larger, higher-risk follow-up, not part of this pass.

## 10. Split-Screen / Multi-Window Support

### 10.1 Manifest

On the main (and only) activity:
```xml
<activity
    android:name=".MainActivity"
    android:resizeableActivity="true"
    android:configChanges="orientation|screenSize|screenLayout|smallestScreenSize|keyboardHidden|uiMode"
    ...>
    <layout
        android:defaultWidth="411dp"
        android:defaultHeight="731dp"
        android:minWidth="300dp"
        android:minHeight="300dp"
        android:gravity="top|end" />
</activity>
```
`configChanges` prevents the activity (and its Compose tree) from being torn down and recreated on every split-screen resize/rotation — important since we don't want the camera `PreviewView` to flicker/reinitialize every time the user drags the split-screen divider. The `<layout>` block matters mainly for freeform/desktop-windowing devices (Chromebooks, some tablets); harmless elsewhere.

**Implementation notes.** Added exactly as specified; verified via `aapt2 dump xmltree` on the built APK that `resizeableActivity`, `configChanges`, and the `<layout>` block's four attributes all merged into the final manifest correctly.

### 10.2 Recording continuity

This is **already solved by construction**: recording lives in a foreground `Service` (ported from Alibi's `RecorderService`/`VideoRecorderService`/`IntervalRecorderService`), not in the `Activity`. Losing window focus, being resized to half-screen, or even the activity being stopped (if the user swipes it away while the service is a proper foreground service with a notification) must **not** stop recording. This is also exactly what §7.4's impact-detection reliability design leans on — verify explicitly during implementation/testing (§15), since a dashcam that stops recording (or drops a pending impact save) when the user opens a navigation app defeats the entire purpose of both the split-screen requirement and the impact-detection feature.

### 10.3 Responsive layout

- Do not hardcode fixed dp widths for the control row or dashboard cards; use `Modifier.fillMaxWidth()` + `weight()` so the control row compresses gracefully at ~360–400dp width (typical half-screen width on a phone in landscape-split or portrait-split).
- At narrow widths, prefer stacking the status card row vertically above the camera preview rather than horizontally, and shrink (don't hide) the secondary icon buttons and the pending-auto-save banner (§9.1) — a dashcam user glancing over from a nav app still needs to see recording/incident state at a glance.
- Test with Android Studio's resizable-emulator / multi-window drag at widths down to ~320dp to ensure no clipped text or unreachable touch targets (all interactive elements ≥48dp per Material touch-target guidance, matching FadCam's existing 48dp icon-button convention).
- Camera access in multi-window: Android grants camera access to any **visible** app regardless of touch/input focus (multi-window camera restrictions are about focus stealing for security-sensitive single-focus scenarios, not general split-screen) — so recording+preview should continue rendering in the non-focused split-screen pane. Flag as a device-specific risk to verify on at least one Samsung (One UI heavily customizes multi-window) and one stock/Pixel device, since OEM multi-window implementations vary.

**Implementation notes.** Rather than guessing at responsive-layout risk in the abstract, every Record/Recordings/Settings-screen composable was actually audited for hardcoded fixed-dp-width containers that could clip below ~360dp (this session's Record/Settings screen rebuild, §9.1/§9.3, was the first real opportunity for this kind of regression). Four real violations were found and fixed, all now proportional/`fillMaxWidth()`-based instead of fixed:
- `VideoRecordingStatus.kt`'s `isStartingRecording` shimmer placeholder was a fixed 128dp box inside a landscape two-panel layout that can squeeze each panel below that at split-screen widths — now `fillMaxWidth(0.6f)`.
- `RecordingStatus.kt`'s progress-bar default was a fixed 300dp — now `fillMaxWidth()`.
- `RecordingRow.kt`'s duration/file-size text (Recordings/Gallery screen) had no `maxLines`/ellipsis guard, unlike its sibling date text — added, so it truncates gracefully instead of crowding once the fixed thumbnail+menu-button chrome eats into a narrow row's width.
- `ThemeSelector.kt`'s preview swatches were pinned to a hardcoded 100dp width in the composable performing the actual sizing, silently defeating the `weight(1f)`/`fillMaxWidth()` modifier its caller passed in expecting it to shrink — now `fillMaxWidth()` internally too.

All interactive touch targets across the audited files were already ≥48dp (icon buttons, FABs, the primary Start button) — no violations found there. The bottom navigation bar (§8.3) uses pure Material3 `NavigationBar`/`NavigationBarItem` defaults with no fixed-width overrides, already responsive.

**What could not be verified in this environment, and is a real gap, not a formality:** none of §10's actual *testing* requirements were performed — there is no camera-equipped device or Android emulator available here. Specifically still unverified: whether the app genuinely continues recording uninterrupted when resized/backgrounded/losing focus in real split-screen (§10.2's core claim rests on the existing foreground-service architecture already being correct, per §7.4/§9.1's implementation, but has not been exercised under real multi-window conditions); the resizable-emulator drag-to-320dp check; and the Samsung-One-UI-vs-stock-Android device variance flagged above. These need real hardware/emulator testing before this section can be considered verified rather than "implemented per spec and locally audited."

## 11. Settings Schema (extends Alibi's `AppSettings`)

Port Alibi's existing `AppSettings` (DataStore + kotlinx-serialization JSON blob, no Room/SQL) and add:

```kotlin
@Serializable
data class WatermarkSettings(
    val enabled: Boolean = true,
    val corner: WatermarkCorner = WatermarkCorner.TOP_LEFT,   // TOP_LEFT/TOP_RIGHT/BOTTOM_LEFT/BOTTOM_RIGHT
    val speedUnit: SpeedUnit = SpeedUnit.KMH,                 // KMH/MPH
)

@Serializable
data class LocationSettings(
    val updateIntervalMs: Long = 1000L,
)

@Serializable
data class ImpactDetectionSettings(
    val enabled: Boolean = true,
    val postImpactDurationMinutes: Int = 5,   // default per requirement; user-configurable
)

// Floating preview window shown while backgrounded during recording (§9.5) — off by
// default, since it requires the special SYSTEM_ALERT_WINDOW permission and shouldn't
// surprise a user who never opted in.
@Serializable
data class PipSettings(
    val enabled: Boolean = false,
)

// Extend the existing VideoRecorderSettings/AppSettings root with:
val watermark: WatermarkSettings = WatermarkSettings()
val location: LocationSettings = LocationSettings()
val impactDetection: ImpactDetectionSettings = ImpactDetectionSettings()
val autoStartOnLaunch: Boolean = true   // §9.1
val pip: PipSettings = PipSettings()    // §9.5
```

Reuse Alibi's existing `AppSettingsSerializer` pattern (add the new fields to the top-level serializable data class; DataStore handles migration of old→new schema gracefully as long as new fields have defaults, same as any kotlinx-serialization default-value addition).

**Implementation notes.** This schema is now complete on `AppSettings`, added across four phases rather than all at once: `WatermarkSettings`/`WatermarkCorner` and `ImpactDetectionSettings` landed early (§5, §7) since `WatermarkTextProvider`/`ImpactDetector` needed real values to be genuinely wired rather than stubbed; `LocationSettings` and `autoStartOnLaunch` landed next; `PipSettings` landed last, alongside §9.5's overlay work, since that feature's gating needs a real `enabled` value to be genuinely wired. `LocationSettings.updateIntervalMs` is wired into `IntervalRecorderService.start()`'s `locationTracker.start(updateIntervalMs = settings.location.updateIntervalMs)` call — it has no settings-screen UI of its own, since §9.3 doesn't list a "Location" card (it's an internal tuning knob, not a user-facing setting). `autoStartOnLaunch` is both schema AND behavior: `RecorderScreen` now has a one-shot `LaunchedEffect` that, on first composition, auto-starts recording if the setting is on, recording isn't already active, and the required camera/audio/storage permissions are already granted — otherwise it silently falls through to the existing manual-start UI (there's no way to auto-grant a runtime permission without user interaction, so requiring a manual tap in that case is the correct fallback, not a gap). A settings toggle (`AutoStartOnLaunchTile`) was added next to the other recording-behavior tiles, and `PipEnabledTile` (§9.3/§9.5) right after it. Forward-compat for `PipSettings` (and every schema addition here) is automatic — `AppSettingsSerializer` uses `ignoreUnknownKeys = true`, so an existing `settings.json` missing a given key just deserializes with that field's default. A fifth, later addition: `VideoRecorderSettings.disableAutofocus: Boolean = false` (§9.1's fixed far-distance focus toggle), alongside that pre-existing `VideoRecorderSettings` group's `targetedVideoBitRate`/`quality`/`targetFrameRate` fields (all inherited from Alibi, so not shown in the code block above) — exposed via a new `VideoRecorderDisableAutofocusTile` in Advanced Settings, next to Quality/Bitrate/Frame Rate. ## 16. Resolved Decisions & Remaining Risks

All initial open questions have been resolved by stakeholder review:

1. **Play Services:** this app must avoid Google Play Services entirely. Resolved by using `LocationManager` (not `FusedLocationProviderClient`, §6) and bundling fonts locally (not Google's Downloadable Fonts provider, §13). This constraint applies to *every* subsystem added going forward, not just these two — treat it as a standing architectural rule, and re-check it whenever adding a new dependency (§15's "No Play Services check").
2. **CameraX version:** use the most recent stable release — pinned to `1.5.1` as of this writing (§5.1, §13); re-verify at implementation time in case a newer stable patch has shipped.
3. **App name:** keep **RoadLog** as the app's name (not a placeholder) — package `app.roadlog.dashcam` unless changed for other reasons; no architectural impact either way.
4. **Impact/hard-braking auto-save:** now fully in scope and designed in detail — accelerometer-based detection, immediate buffer protection, delayed finalize after a configurable duration (default 5 minutes), with process-death survival (§7).
5. **Watermark/UI font:** use a FOSS professional typeface — **Inter** (SIL OFL 1.1) — instead of FadCam's Ubuntu, bundled locally rather than via a Play-Services-dependent font provider (§8.2, §13).
6. **GPLv3 attribution and internal design-provenance comments, a later pass.** Both source repos are GPLv3-licensed, and this app is a genuine derivative work of Alibi specifically — real code was ported (services, `BatchesFolder`, `AppSettings`, the view-model layer, §2.1), not just design ideas. GPLv3 requires preserving attribution/copyright notices in derivative works you distribute, so the About screen's "Based on Alibi" credit + GitHub link (`Constants.kt`'s `ALIBI_REPO_URL`) is a compliance requirement, not leftover branding, and was deliberately kept when a broader cleanup pass removed every OTHER Alibi/FadCam mention from the codebase — dozens of internal "modeled on FadCam's X," "unlike Alibi's Y," "bumped from Z's original N" design-provenance comments across the watermark/theme/location/impact-detection files, none of which were user-visible or load-bearing, all removed per explicit direction rather than kept as historical documentation (the usual convention for this file's own comments, §-numbered inline notes throughout PLAN.md, is unaffected — this was specifically about in-*source* comments). A verbatim copy of the GPLv3 license text (`alibi/LICENSE` and `FadCam/LICENSE` are byte-for-byte identical) was added at the same time, at `THIRD_PARTY_LICENSES/GPLv3-Alibi-and-FadCam.txt` — closing a real gap where `THIRD_PARTY_LICENSES/` previously only had the Inter font's OFL license, with no copy of the GPLv3 text itself despite the app depending on it for the Alibi-derived portions. FadCam itself needed no attribution to begin with, since (per §2.2) only its design language was reimplemented, never its actual code.
7. **Whole-module performance pass (post-launch hardening).** A dedicated audit (Compose recomposition, service/IO threading, DataStore collection patterns) turned up two real bugs beyond pure inefficiency, both fixed alongside the perf work rather than filed separately since their symptoms are resource-consumption issues: (a) `VideoRecorderService.pause()`/`resume()` launched independent, unordered coroutines to close/reopen the camera — a fast pause→resume could let the stale close fire after the fresh reopen and kill the just-resumed session; now serialized with a `Mutex` so close-before-reopen ordering is guaranteed regardless of launch order (a generation counter was considered and rejected — it would only suppress the stale write, not the camera/`HandlerThread` leak underneath a second open); (b) `RecorderEventsHandler`'s manual-save debounce captured `Timer().schedule(...)`'s return value (a `TimerTask`) instead of the `Timer` itself, so `.cancel()` never actually stopped the `Timer`'s background thread — one leaked thread per manual save, now fixed by keeping the real `Timer` reference. Beyond those: `VideoRecordingStatus`/`RecordingControl`/`StorageIndicator` were re-executing in full every second during recording (driven by the elapsed-time tick) because they took the whole unstable `VideoRecorderModel` ViewModel as a parameter instead of the small set of fields they actually read — fixed by hoisting a `remember`-keyed `RecordingUiState`/`RecordingControlActions` pair at the `VideoRecordingStatus` level, matching the Compose idiom for "ViewModel-as-prop defeats skip-recomposition." The Settings screen had up to 7 independent `DataStore.data` collectors alive at once (`ThemeSelector`/`AccentColorPicker`/`ImportExport` each re-subscribing instead of receiving the screen's already-collected `settings`, plus `LockedAppHandlers` collecting the full blob just to check "has it loaded once") — consolidated to thread `settings` through as a parameter, matching the ~13 tiles that already did this correctly. Compose's `experimentalStrongSkipping` compiler flag was also enabled (`app/build.gradle`), letting composables with not-yet-annotated unstable parameters skip via a runtime equality check instead of always re-executing. Splitting `AppSettings`'s single-blob DataStore into multiple stores was considered and explicitly rejected for this pass — all `updateData` call sites are discrete, tap-driven writes (no slider/drag amplification), so the full-blob rewrite cost is bounded by human interaction rate, and splitting it would carry real migration risk for existing `settings.json` files with no matching benefit.

**Remaining implementation risks to budget time for (not blocking, but worth flagging):**
- **CameraX Effects API maturity for dual (preview + encoder) output:** this is the one piece of this plan without a directly-copyable reference implementation in either source repo — prototype `WatermarkSurfaceProcessor` early (§14 step 4) and treat FadCam's `GLWatermarkRenderer.java`/`GLRecordingPipeline.java` as a fallback architectural reference if the official Effects API proves too limited in practice.
- **Impact-detection threshold tuning:** the 2.5–3g starting threshold (§7.1) will need real-world/road-test calibration to balance missed detections against false positives from potholes/speed bumps/loose mounting — expect an iteration cycle here, not a one-shot correct value.
- **GPS fix latency without Play Services:** cold-start fix acquisition via plain `LocationManager` is slower than fused location, particularly indoors/in parking structures — acceptable given the hard Play-Services constraint, but confirm the "-- km/h" fallback UX reads as intentional rather than broken during testing (§15).
